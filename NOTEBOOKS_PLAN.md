## Target architecture

```
NDSharp                 (new NuGet, net10.0, zero Python dependency, MIT)
  NDArray, dtypes, strided views, broadcasting, ufuncs, reductions, indexing,
  linalg (inv/solve/det/eigh/svd/lstsq), fft, random (PCG64 + default_rng, bit-compatible
  with numpy), pad/roll/unique/…           ← the NUMPY_PLAN.md shim, extracted and grown
NDSharp.Image           (new NuGet)   cv2-shaped image operations on NDArray: codecs (imread/imencode/
                                      imwrite), color, filter/blur/Sobel/…, morphology, warp, features, …
NDSharp.Plot            (new NuGet)   matplotlib-shaped plotting that renders to PNG/SVG bytes
NDSharp.Torch           (new NuGet)   tensors + autograd + nn/optim over NDArray (or a TorchSharp bridge — D3)

PySharp.Numpy           (binding)  numpy module: Python-facing surface over NDSharp (PyInstance wrapper,
                                   dunder dispatch, kwargs, repr) — what NumpyModule.cs is today
PySharp.Cv2             (binding)  `import cv2`
PySharp.Matplotlib      (binding)  `import matplotlib.pyplot` (+ patches, cm, mplot3d subset)
PySharp.Torch           (binding)  `import torch / torch.nn / torch.nn.functional / torchvision`

JupyterNet              image display: IKernelOutputSink.WriteImage(mime, bytes) end to end
```

Rules inherited from the project: core packages never reference PySharp; binding packages are opt-in
companions exactly like `PySharp.Sqlite3/Pyodbc/Psycopg2` (v2.0.0 split); the CLI registers all of them;
the existing 14 `M14_Numpy` test files must stay green through the extraction (they are the contract).

### The backend pattern (applies to every library)

NumPy was the first; `cv2`, `matplotlib`, `torch`, `pywt` follow the same recipe:

1. A **native package** `NDSharp.X` with a C# API and **no Python dependency** (errors as `NDException`s,
   arrays as `NDArray`) — usable from any .NET host on its own.
2. A **thin binding** `PySharp.X` (`src/PySharpLib.X`) that only translates Python ⇄ .NET (argument binding,
   scalars, exceptions) and is registered opt-in with `XRegistration.Register(importer)`; the CLI and the
   JupyterNet kernel register all of them.
3. **Verification against the real library**: golden snippets `src/PySharp.Tests/Oracle/<lib>/*.py` whose
   `.expected` output comes from running the same snippet on real CPython (`tools/oracle/make_golden.py`),
   plus native tests with oracle-generated expectations for the .NET API.
4. Each library's **known divergences** are written down in this file, not left implicit.

**Known, deliberate divergences from numpy** (documented so they are not rediscovered as bugs):
- Results of dtype `float64`/`int64`/`bool` are plain Python `float`/`int`/`bool` (fast, no wrapper per
  element); every other dtype yields a numpy scalar instance (`np.uint8(200)`, wraps like numpy).
  Consequences: `type(x).__name__` is `float` not `float64`; repr inside containers shows `1.5` not
  `np.float64(1.5)`; `float32_array * np.float64(2)` stays float32 (numpy 2 makes it float64).
  `isinstance(x, np.floating/np.integer/np.generic)` is true for them via `PyClass.InstanceCheck`.
- float32 transcendental functions (`exp`, `sin`, ...) use .NET's correctly-rounded versions; numpy's SIMD
  kernels differ in the last ulp (seen: `np.exp(np.float32(2))`).
- `numpy.random` is not bit-compatible yet (Phase 2).

**Known divergences added in Phase 2:**
- `eigh`/`svd` use Jacobi methods: eigen/singular **values** match numpy, vector **signs** can differ from LAPACK's
  (`U`, `Vt`, eigenvectors are equal up to a sign per column; outputs are verified sign-independently).
- FFT: results agree with numpy to ~1e-15 but not bit for bit (pocketfft's exact operation order); zero imaginary
  parts of real-input transforms are exact, but the *sign* of a zero (`-0.j`) can differ.
- `inv`/`solve` rounding noise (e.g. `inv(a) @ a` off-diagonals) differs from OpenBLAS (FMA, blocking).
- `argsort` is stable (numpy's quicksort is not, only ties can differ); `float32` `exp/sin/...` ulp-level.

## Verification strategy (no CPython available)

1. **Probe-driven:** `tools/notebook_probe.ps1` — modules importable + `np.*` coverage, per notebook.
2. **Runner (Phase 4+):** extend the probe to execute each notebook's code cells in one PySharp session
   (cell state carried like `PySharpKernel`), recording first failing cell + exception, matplotlib
   headless; result table appended to NOTEBOOKS_BASELINE.md.
3. **Invariants:** identities the notebooks assert/print (orthogonality, round-trips, Parseval, known
   closed forms), image statistics bounds, comparison against hand-computed small cases.
4. **Read the real source** (numpy, OpenCV docs/source) for exact semantics — never guess
   (saturation rules, rounding half-to-even in `np.round`, border modes, PCG64 constants).
5. Optional oracle (D4): one-off CPython+numpy+OpenCV install used **only** to dump golden
   outputs into test fixtures, never as a runtime dependency.

## Risks

- **Scale:** 129 cv2 + 93 torch symbols is a multi-week surface; hence tiers and per-block milestones.
- **Numerical parity** (PCG64 streams, `float32` rounding, saturating uint8 math, interpolation
  kernels) decides whether lesson outputs look "right"; budget time for it in Phase 2/4.
- **Performance:** a Python-in-C# interpreter looping over pixels will be slow where notebooks use
  Python loops (lessons 4, 17, 19, 25, 35) — measure, and push hot paths into NDSharp.
- **Native dependencies** (SkiaSharp, OpenCvSharp, libtorch) vs the "pure .NET, no native deps"
  ideal of the core: confined to the optional `NDSharp.*`/binding packages by design.
- **Interpreter gaps** the notebooks will surface (class subclassing of native classes, f-string
  formats, `with` on tar/open, comprehension edge cases) — fixed in PySharpLib as found, with tests.
